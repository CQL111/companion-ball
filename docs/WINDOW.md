# 窗口与灯塔
## 漂流瓶主页 · 运营后台 · 产品设计

> **一句话**：前台是**窗口**——站在屋里看海；后台是**灯塔**——有人值班，保证海上不出事。
> 两者都不是社区。这份文档设计的是「不像社区的社区产品」，以及它背后那间必须有人守着的值班室。
>
> 基础设施（Workers / D1 / R2、域名 boringtime.cn、费用、monorepo）见 [`PLATFORM.md`](PLATFORM.md)；
> 私池规则见 [`SERVER.md`](SERVER.md)；为什么社交要排在私人闭环之后见 [`PRODUCT-THESIS.md`](PRODUCT-THESIS.md)。

## 一、结论先行

| # | 决策 | 理由 |
|---|---|---|
| 1 | **它不是社区，是「海边的窗口」** | 社区的功能是「让人互相连接」；我们的功能是「让人确认别人也醒着」，然后**断开**。 |
| 2 | **前台没有任何互动通道** | 没有评论、没有回复、没有点赞、没有关注、没有私信、没有用户主页。唯一的动作是「看下一页」和「下载」。 |
| 3 | **瓶子没有独立 URL** | 不可分享、不可被搜索引擎索引、不可递归跳转。想传播？截图可以，但那是人的自由，不是我们给的通道。 |
| 4 | **后台看不到私池** | 管理员只能看两样东西：用户主动公开的橱窗、被别人举报的内容。这是隐私承诺的技术保证，不是自觉。 |
| 5 | **新闻是「海上的消息」，不是资讯流** | 官方编辑、每天最多一条、没有评论区、没有外链跳转。它进笔记本，所以必须可控、可撤、可追溯。 |

**投资视角**：网页不承担变现，它承担两件事——**获客**（下载入口）和**信任**（证明这不是一个收割注意力的产品）。
唯一要优化的转化是「看海 → 下载一只猫」。任何让人在网页上停留更久的设计，如果换不来这个转化，就不做。

## 二、它像社区的地方，和不像的地方

用户说「类似社区但不是传统社区」。这句话是对的，但需要精确：

| 维度 | 传统社区 | 我们 |
|---|---|---|
| 身份 | 昵称 + 头像 + 主页 + 粉丝数 | **随机代号**（「夜里的橘子」），每次投递重新生成，跨瓶不可关联 |
| 关系 | 关注 / 好友 / 私信 | **无任何持久关系**。读完即断 |
| 内容 | 无限流 + 推荐算法 | **按时段分栏 + 有限翻页**。海就只有这么大 |
| 互动 | 点赞 / 评论 / 转发 / 收藏 | **零互动**。没有可点的按钮 |
| 数字 | 阅读量 / 点赞数 / 排名 | **一个数字都不显示**（延续客户端的「不说数据」红线） |
| 留存 | 签到 / 等级 / 积分 / 通知 | **无任何召回机制**。想来就来 |
| 商业模式 | 广告 / 会员 / 打赏 | **不做**。变现只在年度本与装饰付费 |

**我们只借用传统社区的一样东西：在场感。**

一个陌生人在凌晨两点写了一句「今天面试没过，但我没哭」，你读到了——你知道此刻世界上还有别人也没睡。
这就够了。**我们不给任何方式让你去联系 ta**，因为一旦可以联系，这件事就从「共鸣」变成了「社交」，
而从社交开始，产品就要面对骚扰、诈骗、内容审核、用户成长体系——那是一条我们打不赢的赛道。

> **产品定位一句话**：我们卖的不是「认识新朋友」，是「不必认识也能被理解」。

### 因此刻意不做

| 不做 | 原因 |
|---|---|
| 用户主页 / 关注 / 粉丝 | 建立可追踪身份 = 社交压力 + 骚扰入口 |
| 评论 / 回复 / 点赞 | 网页 UGC 无设备令牌，刷屏成本趋近于零 |
| 无限滚动 / 个性化推荐 | 推荐需要画像；我们没有画像，也不想要 |
| 搜索功能 | 能搜到内容 → 内容被消费而不是被遇见；也方便爬虫 |
| 排行榜 / 精选 / 热度 | 一旦有「热门」，写的人就会为热度写 |
| 网页端投稿 | 无身份 = 无成本限制；想写就下载一只猫（这也是一条获客路径） |
| 私信 / 联系方式交换 | 见上；正则拦截 + 举报下架只是兜底 |

## 三、设计语言：海、窗口、灯塔

统一隐喻，让前端文案、后台命名、指标口径都说同一套话。这不算花活——它让团队在争论「要不要加个评论」
的时候有一个共同的判断标准：**这东西属于海，还是属于广场？**

| 隐喻 | 指代 | 出现位置 |
|---|---|---|
| **海面** | 漂流瓶内容池 | 前台 |
| **潮汐** | 四个时段分池（深夜 / 清晨 / 白天 / 傍晚） | 前台、后台筛选器 |
| **窗口** | 网页本身 | 前台 |
| **静读** | 打开一条瓶子的阅读态 | 前台 |
| **沉海** | 7 天无人捡 → 删除 | 前后台 |
| **灯塔** | 运营后台 | 后台 |
| **守塔人** | 管理员 | 后台 |
| **值班** | 审核队列 | 后台 |
| **封海** | `EMERGENCY_OFF` | 后台 |

## 四、前台：漂流瓶主页

### 4.1 信息架构

```
/                     首页：一句话 + 此刻的海 + 下载
/gallery              窗口（默认打开当前时段）
/gallery?pool=night   指定潮汐：深夜 / 清晨 / 白天 / 傍晚
/news                 海上的消息（列表）
/news/:id             消息详情（唯一有独立 URL 的内容类型）
/download             下载页（已有，扩展）
/privacy /terms       法务（与客户端同源生成，见 PLATFORM 第四节）
```

**没有** `/user/*`、`/profile/*`、`/bottle/:id`、`/search`。

### 4.2 首页

一屏之内说完三件事：这是什么、现在海上有什么、去哪儿拿一只猫。

```
┌──────────────────────────────────────────────┐
│  桌面陪伴 · 团子猫                             │
│                                              │
│  有人在凌晨两点写下一句话，                     │
│  另一个人在清晨捡到了它。                       │
│                                              │
│  [下载 Windows 版]   [看看此刻的海 →]          │
├──────────────────────────────────────────────┤
│  此刻 · 深夜                                  │
│  ┌────────┐ ┌────────┐ ┌────────┐           │
│  │ 瓶子卡  │ │ 瓶子卡  │ │ 瓶子卡  │           │
│  └────────┘ └────────┘ └────────┘           │
│              看更多深夜的瓶子 →                │
├──────────────────────────────────────────────┤
│  海上的消息                                   │
│  · 今天下雨了，我把尾巴收了起来                  │
└──────────────────────────────────────────────┘
```

规则：
- **首页只展示 3 条**，且**不展示任何数字**（没有「已有 N 条」）
- 空海时（冷启动）诚实说：「海面还很安静。你是最早来的人之一。」——**不伪造活动**
- 下载按钮是页面上**唯一的强调色元素**；其余全部低饱和

### 4.3 窗口（橱窗流）

这是「读」的主体。核心设计是**潮汐**：不是无限流，而是「此刻这一片海」。

| 规则 | 说明 |
|---|---|
| 默认池 = 访客本地时间所在时段 | 凌晨打开看到的是深夜瓶，中午看到的是白天瓶 |
| 可手动切换四档 | 让用户感到「海是完整的」，不是只有自己那一小块 |
| 每池最多 20 条，游标分页 | 有限。翻到底就是「今天海上只有这么多」 |
| 排序 = 随机稳定排序 | 不按时间、不按热度。同一访客同一天顺序一致（用访客 cookie 做种子），避免每次刷新都变 |
| 卡片内容 | 正文（≤60 字）+ 随机代号 + 时段标签。**不含**作者、设备、时间、任何计数 |
| 卡片不可链接 | 点击进入**静读模式**（见 4.4），不产生 URL |
| `noindex, nofollow` | 全程不索引、不追链接。防爬、防用户 Google 到自己写的话 |
| 撤回联动 | 作者在桌面端撤回 → 橱窗副本立即下架（`withdrawn`） |

**为什么是随机稳定排序而不是按时间**：按时间排会让「早发的人永远在后面」，也会诱导写作者卡点发。
随机稳定 = 每次来顺序不变（不会觉得页面在动），但不同人来看到的排列不同（没有「第一屏霸权」）。

### 4.4 静读模式

点击一张卡片后，不是跳转，是一个**全屏、变暗、无操作**的阅读态。

```
┌──────────────────────────────────────────────┐
│                                    [关闭 ×]  │
│                                              │
│                                               │
│       今天面试没过，但我没哭。                   │
│                                               │
│                        —— 夜里的橘子 · 深夜     │
│                                               │
│                                               │
│         [← 上一张]        [下一张 →]           │
└──────────────────────────────────────────────┘
```

**设计要点**：
- 全屏变暗，正文居中，字号大（这是「读」，不是「刷」）
- 没有任何按钮能对这个瓶子做动作——**没有回复、没有点赞、没有举报以外的东西**
- 「举报」放在角落，弱化（`text-3` 色，hover 才显现）
- 键盘 `←` / `→` / `Esc` 可操作
- **不进浏览器历史**（用 `history.replaceState`，关闭后回到原位置）

**为什么不做瓶子详情页**：详情页意味着可分享 URL → 外部可引用 → 评论在其他平台生长 → 内容在不可控的地方被讨论。
截图是人的自由，但**我们不给通道**。这一个决定省掉了整个「内容外流治理」问题。

### 4.5 海上的消息（新闻）

官方编辑，猫的口吻，每天最多一条。

| 规则 | 说明 |
|---|---|
| 唯一有 URL 的内容（`/news/:id`） | 官方内容，SEO 无害，也是产品被搜索引擎发现的入口 |
| 无评论区 | 新闻不是讨论区 |
| 无外链跳转 | 只展示「来源名」文本，**不给 `<a>`**（避免导流与钓鱼，也与客户端一致） |
| 分类 | `rain` 雨 / `night` 夜 / `city` 城市 / `cat` 猫 / `other` |
| 桌面端联动 | `GET /v1/news/pick` 每设备每天 ≤1 条 → `core/news.ts` 生成一句观察 → 进笔记本 |
| 可撤可改 | 已发布的仍可下架（`archived`），但已在用户笔记本里的不会回收——所以发布前必须预览两次 |

**「猫的口吻」是谁**：选稿可以来自人工选题或**外部爬虫提供的线索**（见第五节），但**成文必须重写**，不全文转载（版权）。
文风约束与客户端一致：第一人称、说感受不说数据、不制造焦虑、不超过 200 字。

### 4.6 冷启动：最难的不是技术

空海是这类产品最大的失败模式。页面再美，第一条内容都没有就没意义。

**三层冷启动**（按优先级）：

1. **私池邀请制**（已定，见 ROADMAP S5）：先让 20–50 个真实用户互投，从私池里
   挑**用户主动勾选了公开**的瓶子进入橱窗。**这是唯一「真实」的来源。**
2. **官方种子瓶**：产品团队以普通用户的口吻写，后台标 `seed = 1`。规则：
   - **前台不做任何区分标记**（区分就破坏了「海」的幻觉）
   - **但后台必须有标记**（运营需要知道哪些不是真的）
   - 总量上限为真实内容的 50%，真实内容每增加 1 条，种子最多保留 1 条
   - 种子**永不进入私池**，用户捡不到，也就不存在「我回了官方瓶子没人理」的失望
3. **首页诚实提示**：当橱窗内容 < 10 条时，显示「海面还很安静」——**不用伪造的数字撑场面**

> **底线**：我们可以在内容上「借位」，但**不能在活动数据上撒谎**。
> 不出现「已有 10,000 人在此倾诉」这类虚构数字。这是产品诚信的锚点。

## 五、外部线索管道（爬虫系统接入）

> 新闻线索的唯一来源。WINDOW 第五节。

> **决策**：新闻的**线索**由独立的爬虫系统提供，不在本仓库实现。
> 本仓库只定义「线索」的**接收契约**与「如何用它写稿」。

#### 为什么线索和成文必须分开

| 如果爬虫直接产出新闻 | 后果 |
|---|---|
| 自动转述 → 事实错误无人负责 | 新闻进用户笔记本，说错话是要负责的 |
| 全文转载 → 版权风险 | 我们不能做聚合器 |
| 无人把关 → 钓鱼/导流链接 | 与「不出现任何外链」的红线冲突 |
| 爬虫挂了 → 新闻断更 | 内容管道与运营解耦才能各自演进而互不影响 |

**所以**：爬虫只负责「发现」，人负责「判断」和「成文」。爬虫产出的永远是 `draft`，
**没有任何自动发布路径**——这是硬规则，写进 API 契约（线索接口不提供 `publish` 字段）。

#### 线索契约（v1，由本仓库定义，爬虫侧实现）

```ts
// packages/contracts/src/news.ts —— 三端共用（web / admin / server）
export interface NewsLead {
  /** 线索 id（爬虫侧生成，幂等键） */
  id: string
  /** 原始标题（用于编辑判断，不会直接展示给用户） */
  rawTitle: string
  /** 原始摘要（≤500 字，供编辑参考） */
  rawSummary: string
  /** 来源名（如「中国气象局」），最终展示给用户的只有这个 */
  sourceName: string
  /** 来源 URL：存库，但**前台永不渲染成链接** */
  sourceUrl: string
  /** 分类建议（爬虫给的，编辑可否决） */
  suggestedCategory: 'rain' | 'night' | 'city' | 'cat' | 'other'
  /** 抓取时间 */
  fetchedAt: number
  /** 线索指纹：用于去重与「这条看过了」 */
  fingerprint: string
}

/** 推送线索：爬虫 → 服务端，使用独立的 service token，而不是 admin 会话 */
export interface NewsLeadPush {
  token: string          // 环境变量 NEWS_INGEST_TOKEN，与管理员凭据分离
  leads: NewsLead[]      // 单次 ≤ 50 条
}
```

| 接口 | 方向 | 说明 |
|---|---|---|
| `POST /v1/internal/news/leads` | 爬虫 → 服务端 | 推送线索批次；按 `fingerprint` 幂等去重 |
| `GET /v1/internal/news/leads?status=` | 后台读 | 只在 admin 后台「线索」页，前台不可见 |

**安全**：
- 走**独立 service token**（`NEWS_INGEST_TOKEN`，通过 `wrangler secret` 配置），**不复用管理员 Key**
- 爬虫 token 只能写 `news_leads`，**没有任何读业务数据或发布的能力**
- 限流：单次 ≤50 条、每天 ≤20 批；超限拒绝并告警
- 线索表 30 天自动清理（只看新鲜的）

#### 数据模型增量

```sql
-- 线索（爬虫提供，等待编辑消化）
CREATE TABLE news_leads (
  id            TEXT PRIMARY KEY,
  fingerprint   TEXT NOT NULL UNIQUE,     -- 幂等去重
  raw_title     TEXT NOT NULL,
  raw_summary   TEXT NOT NULL,
  source_name   TEXT NOT NULL,
  source_url    TEXT NOT NULL,
  suggested_category TEXT NOT NULL,
  fetched_at    INTEGER NOT NULL,
  status        TEXT NOT NULL,            -- new | used | ignored
  used_news_id  TEXT,                     -- 消化成哪条新闻
  created_at    INTEGER NOT NULL
);
CREATE INDEX idx_leads_status ON news_leads(status, fetched_at);
```

#### 后台「线索」页

在「海的记录」下新增一个 tab：

```
线索 24 条待看          [全部] [雨] [夜] [城市] [猫]
┌──────────────────────────────────────────┐
│ 中国气象局 · 雨 · 12 分钟前                 │
│ 标题：江南梅雨季提前到来                    │
│ 摘要：预计未来一周…（爬虫抓的原摘要）        │
│ [用它写一条]  [忽略]                        │
└──────────────────────────────────────────┘
```

- 「用它写一条」→ 跳到新闻编辑器，预填来源与正文草稿（原文摘要，供编辑改写）
- 「忽略」→ `status=ignored`，同 fingerprint 不再提示
- 线索**不做任何自动处理**：没有「一键转成新闻」，因为「改写」是不可省略的人的工作

#### 爬虫系统的工程约定（给后续实现用）

| 项 | 约定 |
|---|---|
| 部署 | 独立进程/容器，**不进本 monorepo**（不同节奏、不同资源） |
| 输出 | 只认上面的 `NewsLeadPush` 契约；契约在本仓库 `packages/contracts`，爬虫侧作为依赖引用 |
| 频率 | 建议 30–60 分钟一批；只抓「过去 24 小时」的增量 |
| 去重 | 必须自己生成稳定 `fingerprint`（规范化标题 + 来源域） |
| 失败 | 指数退避重试；服务端不通时本地排队，不丢线索 |
| 合规 | 遵守 robots.txt；只存标题/摘要/URL，**不存全文**；注明来源 |

> **为什么爬虫不进 monorepo**：它的依赖（抓取框架、解析库、可能还要无头浏览器）、发布节奏、
> 资源占用都与产品站点完全不同。契约在本仓库，实现在外面——这和 `packages/server` 可迁 VPS 是同一个思路。

## 六、后台：灯塔值班室

### 6.1 角色

| 角色 | 能做什么 | 谁 |
|---|---|---|
| `viewer` | 只看：概览、列表、审计 | 将来的运营外包、投资人演示 |
| `operator` | + 审核（批准/驳回/隐藏）、新闻编排 | 日常值班 |
| `admin` | + 开关、账号管理、封禁设备 | 我自己（第一年 ≤ 3 个账号） |

登录方式见 [`PLATFORM.md`](PLATFORM.md) 第六节（API Key + TOTP，免费档可跑）。
**邀请制、无公开注册、无找回**（Key 丢了由管理员重置）。

### 6.2 信息架构

```
灯塔
├── 概览          今天的海面（不是 KPI dashboard）
├── 值班          审核队列：橱窗待审 / 被举报
├── 海的记录      新闻编排（草稿 → 定时 → 发布 → 归档）
├── 瓶子          橱窗内容管理（下架 / 恢复 / 封禁设备）
├── 封海          紧急开关
├── 审计          谁在什么时候做了什么
└── 守塔人        账号管理（仅 admin）
```

**刻意没有的模块**：
- ❌ 用户管理（我们没有用户账号）
- ❌ 私池浏览（**管理员看不到私池**，见 6.5）
- ❌ 消息 / 通知中心（没有「用户来信」这个概念）

### 6.3 概览：今天的海面

后台首页不做成 BI 大屏。它回答一个问题：**今天要做什么？**

```
┌────────────────────────────────────────────┐
│  今天的海面                                  │
│                                            │
│  待审 12   ·   被举报 3   ·   今日新增 8      │
│                                            │
│  ⚠ 3 条举报待处理（最久 4 小时前）            │
│  ⚠ 橱窗今日已发布 0 条（建议 1 条）           │
│                                            │
│  近 7 天                                     │
│  瓶子被捡率 62%   回信率 18%   举报率 0.3%    │
│                                            │
│  [去值班 →]                                 │
└────────────────────────────────────────────┘
```

规则：
- **第一屏是「待办」，不是「数据」**
- 只放 3 个核心比率（被捡率 / 回信率 / 举报率），不做图表堆砌
- 有异常才用强调色（举报积压 > 2 小时、举报率 > 0.5%、服务处于封海状态）
- **不显示 DAU、停留时长、访问量**——这些是社区指标，会诱导我们做社区的事

### 6.4 值班：审核队列

两个 tab：**橱窗待审** / **被举报**。

**橱窗待审**（用户投瓶时勾选了「可以让别人在网页上看到」）：

```
┌────────────────────────────────────────────┐
│  待审 12 条         [全部] [含敏感词] [最长等待] │
├────────────────────────────────────────────┤
│  今天面试没过，但我没哭。                     │
│  —— 夜里的橘子 · 深夜 · 6 小时前              │
│  来源：私池瓶 #a3f2（作者已勾选公开）           │
│                                            │
│  ⚠ 含联系方式风险词：无                       │
│                                            │
│  [批准]  [驳回]  [封禁该设备]                  │
└────────────────────────────────────────────┘
```

| 操作 | 后果 | 可否撤销 |
|---|---|---|
| 批准 | `status=approved`，`expires_at = now + 30 天`，进入橱窗 | 可下架 |
| 驳回 | `status=rejected`，不展示，**不通知作者**（无回声原则） | 可改判 |
| 封禁设备 | 吊销令牌，该设备所有接口 401 | 可解除（`revoked_tokens` 删行） |

**被举报**：展示被举报的正文 + 原因 + 举报数。三个动作：**下架**（`hidden=1`）/ **保留**（标记已处理）/ **封禁设备**。
被举报内容即使是私池里的，**管理员在这一屏能看到**——这是隐私边界唯一的窄缝，见 6.5。

**审核纪律**：
- 每条决策都进审计日志（`actor` = 管理员 id，不是邮箱）
- 驳回不写理由给用户（没有通知通道），但后台必填内部备注
- **2 小时内必须处理**——这是对用户的承诺，也是后台概览的红色告警线

### 6.5 隐私边界：管理员看不到私池（关键架构决策）

这是本文档里**唯一一条必须写进代码、不能只写进制度**的规则。

| 数据 | 前台 | 后台 | 说明 |
|---|---|---|---|
| 私池瓶子（未公开） | ❌ | ❌ **完全不可见** | 管理员没有任何页面、任何 API 能读它 |
| 私池瓶子（被举报） | ❌ | ✅ 仅该条 | 举报人对这条内容行使了「请人看」的权利 |
| 橱窗瓶子（已批准） | ✅ | ✅ | 用户主动公开 |
| 橱窗待审 | ❌ | ✅ | 审核必需 |
| 回信内容 | ❌ | ❌ | 回信不可公开，也不可审核——只有举报能触达 |
| 设备令牌 | ❌ | ❌ 仅哈希 | 后台只能「封禁某哈希」，看不到设备任何信息 |

**技术保证**（不是自觉）：
- Admin API 的所有查询**只从 `gallery_bottles` / `news` / `reports` 取数**，
  不引入 `bottles` 表（被举报的除外，走一条独立、只按 `id` 精确查询的接口）
- 这条约束写成测试：grep admin handler 里不出现 `FROM bottles`（除举报白名单接口）
- 后台不提供「按作者查瓶子」的能力——只提供「按哈希封禁」

> 为什么值得这么严格：我们的核心资产是**用户敢写真的话**。
> 一旦用户意识到「管理员能读所有私信」，那种真实感就没了。这条边界比任何功能都值钱。

### 6.6 海的记录：新闻编排

| 状态 | 含义 | 谁触发 |
|---|---|---|
| `draft` | 草稿，可编辑 | operator |
| `scheduled` | 已排期（`publish_at`） | operator |
| `published` | 已发布，桌面端可拉到 | 定时器 / 手动 |
| `archived` | 已下架，前台不可见 | operator |

**编辑器要点**：
- 标题 ≤ 30 字、摘要 ≤ 60 字、正文 ≤ 200 字（硬限制，写死在表单里）
- 封面图可选，传 R2（> 500KB 自动拒绝）
- 右侧**实时预览**：显示成「桌面端笔记本里的样子」，而不只是网页样式
  ——因为新闻的主要消费场景是笔记本，不是网页
- 发布前二次确认：「这条会进入用户的笔记本，发出后不能收回」
- 来源字段：`source_name`（只填名字，如「中国气象局」），**允许填 URL 但前台不渲染成链接**

### 6.7 封海：紧急开关

一个大红色的页面，四个开关，每个都有「为什么需要它」的一句话说明：

| 开关 | 关掉什么 | 什么时候用 |
|---|---|---|
| `EMERGENCY_OFF` | 所有写接口（扔 / 捡 / 回 / 举报） | 被刷、被攻击、发现严重漏洞 |
| `GALLERY_OFF` | 橱窗展示（前台显示「窗口暂时关闭」） | 出现待处理的有害内容、合规要求 |
| `NEWS_OFF` | 新闻拉取 | 发错内容、来源版权问题 |
| `REPLY_OFF` | 仅关闭回信 | 回信被滥用（扔瓶仍开） |

**规则**：
- 每个开关改变都必须**填理由**，进审计
- 开关状态写 KV，秒级生效，**不经过后台服务器**——即使后台挂了也能用 `wrangler kv key put` 改
- 概览页顶部常驻显示「当前封海状态」，开着就是红色横幅

### 6.8 审计与守塔人

- **审计**：只追加。登录成功/失败、所有写操作、开关变更、审核决策。保留 1 年。
  展示成时间线（谁 / 何时 / 做了什么 / 对什么），支持按 actor 和 action 筛选。
- **守塔人**：创建账号、改角色、停用、重置 API Key（旧 Key 立即失效）。
  创建时**只展示一次**新 Key + TOTP 二维码，之后永不显示。

## 七、数据模型增量

在 [`SERVER.md`](SERVER.md) 现有表之上增加。**注意 `gallery_bottles` 与私池 `bottles` 是两张独立的表**——
不共用生命周期、不共用审核状态（理由见 [`PLATFORM.md`](PLATFORM.md) 第四节）。

```sql
-- 橱窗：独立表，内容是批准时的快照
CREATE TABLE gallery_bottles (
  id            TEXT PRIMARY KEY,
  source_bottle TEXT,                  -- 来源私池瓶 id；官方种子为 NULL
  pool          TEXT NOT NULL,          -- night | morning | day | evening
  body          TEXT NOT NULL,          -- 快照，不随私池变化
  alias         TEXT NOT NULL,
  status        TEXT NOT NULL,          -- pending | approved | rejected | withdrawn
  seed          INTEGER NOT NULL DEFAULT 0,  -- 1 = 官方种子（仅后台可见）
  sort_key      INTEGER NOT NULL,       -- 稳定随机排序种子
  reviewed_by   TEXT,
  reviewed_at   INTEGER,
  review_note   TEXT,                   -- 内部备注，前台永不展示
  created_at    INTEGER NOT NULL,
  expires_at    INTEGER                 -- approved + 30 天
);

CREATE INDEX idx_gallery_list ON gallery_bottles(status, pool, expires_at);
CREATE INDEX idx_gallery_source ON gallery_bottles(source_bottle);

-- 新闻
CREATE TABLE news (
  id          TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  summary     TEXT NOT NULL,
  body        TEXT NOT NULL,
  source_name TEXT,
  source_url  TEXT,                    -- 存，但前台不渲染成链接
  category    TEXT NOT NULL,           -- rain | night | city | cat | other
  cover_key   TEXT,
  status      TEXT NOT NULL,           -- draft | scheduled | published | archived
  publish_at  INTEGER,
  created_by  TEXT,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER
);

CREATE INDEX idx_news_list ON news(status, publish_at);

-- 每设备看过哪条（每天 ≤1 条）
CREATE TABLE news_seen (
  device_hash TEXT NOT NULL,
  news_id     TEXT NOT NULL,
  seen_at     INTEGER NOT NULL,
  PRIMARY KEY (device_hash, news_id)
);

-- 后台账号与会话（见 PLATFORM 第六节）
CREATE TABLE admin_users       ( /* id, username, key_hash, totp_secret, role, disabled, … */ );
CREATE TABLE admin_sessions    ( /* token_hash, admin_id, expires_at */ );
CREATE TABLE admin_login_attempts ( /* key, window, attempts */ );
CREATE TABLE audit_log         ( /* id, actor, action, target, detail, created_at */ );

-- 聚合统计：只有计数，没有个体
-- 存在的理由：概览页要显示「被捡率 / 回信率 / 举报率」，这三个必须是真实数字
CREATE TABLE daily_stats (
  day             TEXT PRIMARY KEY,     -- YYYY-MM-DD（UTC）
  bottles_thrown  INTEGER NOT NULL DEFAULT 0,
  bottles_picked  INTEGER NOT NULL DEFAULT 0,
  replies_sent    INTEGER NOT NULL DEFAULT 0,
  reports_received INTEGER NOT NULL DEFAULT 0,
  gallery_views   INTEGER NOT NULL DEFAULT 0,
  news_views      INTEGER NOT NULL DEFAULT 0,
  download_clicks INTEGER NOT NULL DEFAULT 0,
  downloads       INTEGER NOT NULL DEFAULT 0
);
```

**为什么单独一张 `daily_stats` 而不是实时聚合**：
- D1 免费档的读额度有限，概览页每次刷新都跑全表聚合会很快耗尽
- 聚合进 cron（每 10 分钟跑一次）用 UPDATE +1，成本极低
- 这张表**只有计数器**，不含任何设备、IP、时段之外的个体信息

**保留策略**：私池过期 7 天删；橱窗下架 30 天删；举报 90 天删；审计 1 年；新闻永久（可归档）；
`daily_stats` 永久（单行/天，3 年也才 1 千行）。

## 九、内容安全与运营

### 8.1 分层防线（按成本从低到高）

| 层 | 做什么 | 成本 | 覆盖 |
|---|---|---|---|
| 1. 技术校验 | 非空、≤60 字、正则拦截手机号/微信号/QQ/URL | 零 | 私池 + 橱窗 |
| 2. 事前审核 | 橱窗必须人工批准才能展示 | 每条 30 秒 | 只覆盖公开内容 |
| 3. 事后举报 | 用户举报 → 2 小时内处理 | 事件驱动 | 私池 + 橱窗 |
| 4. 封禁 | 吊销设备令牌 | 事件驱动 | 全部接口 |

**为什么不做事前审核私池**：私池是「两个人的事」，审核它 = 我们读所有私信，直接违背 6.5 的隐私承诺。
私池靠正则 + 举报兜底；**公开内容**才付人工审核成本。这是产品选择的自然结果。

### 8.2 运营节奏（每天 15 分钟）

| 时间 | 做什么 |
|---|---|
| 早上 | 过一遍待审 + 举报（通常 < 10 条）；发一条新闻 |
| 晚上 | 看一眼概览的 3 个比率；有异常才动 |

**每月复盘一次**：举报率趋势、驳回率（太高说明审核标准不清）、种子占比（太高说明海是假的）。

### 9.3 地区策略（已定：先海外）

**已决定：先做海外版**，代价是早期用户少，但换来：

| 项 | 海外（先做） | 国内（暂缓） |
|---|---|---|
| UGC / 新闻公开站的资质 | 不涉及 ICP / 网络文化经营许可 | 需备案 + 内容资质，办理周期以月计 |
| UGC 审核责任 | 平台自律 + 举报 | 属地监管，需更重的审核与留痕 |
| 支付/变现 | Cloudflare 站点无需备案即可上线 | 先备案才能挂支付 |
| 用户规模 | 小 | 大 |

**执行方式**：
- 公开站（`/gallery`、`/news`、下载页）与 API 同源：`boringtime.cn`（单 Worker，见 PLATFORM 第三节同源部署）
- 桌面客户端不区分地区；只是服务端默认地址指向海外实例
- **国内可访问性**：`workers.dev` 在国内不可达（已踩过），面向国内的服务器按
  [`VPS-DEPLOY.md`](VPS-DEPLOY.md) 自建。**但公开站先只开海外**——国内用户此刻可以用桌面端
  的私人闭环（不依赖公开站），公开内容等资质与合规准备好再开

> 这条策略不是「永远不做国内」，是「先用海外验证产品，再决定为国内付合规成本」。
> 拿资质前把公开站做成「需要邀请口令才能看」，是不需要资质的过渡方案（见 8.4）。

### 9.4 过渡方案：邀请口令（取得资质前）

若将来要在国内开公开站但资质未就绪：

- Worker 侧一个简单的口令校验（环境变量存的哈希）守住 `/gallery` 与 `/news`
- 只有拿到口令的用户能看；口令通过桌面端「领取」或邀请名单发放
- 公开站**零 SEO**（既然要口令，也顺手全站 `noindex`）
- 优点：内容仍然被真实用户消费，产品假设仍可验证；缺点：没有自然流量

> 这个方案写在这里是**为了不让「等资质」成为停摆的借口**。有口令，就能先跑起来。

## 十、指标：该看的，和刻意不看的

### 11.1 该看的（北极星：语言资产厚度）

| 指标 | 口径 | 目标 | 为什么看它 |
|---|---|---|---|
| 瓶子被捡率 | 被捡次数 ≥1 的瓶子 / 总瓶子 | > 60% | 内容有没有人接住 |
| 回信率 | 有回信的瓶子 / 被捡瓶子 | > 15% | 接住之后有没有回应 |
| 举报率 | 举报数 / 被捡数 | **< 0.5%** | 安全底线，超了就必须停 |
| 橱窗 → 下载转化 | 下载点击 / 橱窗访客 | > 3% | 网页有没有完成获客使命 |
| 读者回访率 | 7 天内 ≥2 次访问 / 访客 | > 25% | 「窗口」值不值得再来一次 |
| 页边留句率 | 周内留过 ≥1 句 / 打开笔记本的人 | > 30% | **P2 闸门**（ROADMAP 第七节） |

### 11.2 刻意不看的

| 不看 | 原因 |
|---|---|
| DAU / MAU | 陪伴产品不该用「每日活跃」考核——用户不需要每天来 |
| 停留时长 | 网页停留越久 ≠ 越好；我们想让人「看一眼海，下载，走」 |
| 访问量 / PV | 虚荣指标，会诱导做 SEO 和刷量 |
| 内容量 | 海面越大越好是错的；有限才有「遇见」的感觉 |
| 点赞 / 收藏 / 转发 | 根本不提供 |

> **投资视角**：这套指标体系本身就说明了产品性质——它是一个**低频、高情感、低变现**的产品。
> 它的价值在年度本（一次性高毛利）和品牌，不在日活。如果有人拿 DAU 来考核它，方向就错了。

## 十一、闸门与排期

### 11.1 前置条件

### 11.2 分阶段交付

| 阶段 | 范围 | 人日 | 能验证什么 |
|---|---|---|---|
| **M0 · 窗口最小版** | 首页 + 橱窗流 + 静读模式 + 下载页；后台只有「登录 + 待审队列 + 封海」 | 10–12 | 网页有没有人看、审核管道通不通 |
| **M1 · 海的记录** | 新闻编排 + 桌面端 `news/pick` 接入 | 6–8 | 新闻进笔记本后用户反应如何 |
| **M2 · 灯塔完整版** | 概览 + 审计 + 账号 + 聚合统计 + 举报处置 | 6–8 | 运营 15 分钟/天是否可持续 |
| **M3 · 冷启动运营** | 种子内容、邀请、文案打磨 | 续 | 举报率、回信率是否达标（S5 验收） |

**合计约 22–28 人日**（不含 S3 部署、不含视觉设计）。

### 11.3 先后顺序的理由

1. **先窗口，后新闻**：窗口验证的是「海面有没有人看」，是产品假设；新闻只是内容补充。
2. **先审核，后概览**：没有内容就不需要 dashboard；先让审核跑起来，才知道该统计什么。
3. **后台最后做完整版**：早期只有 1 个人用，15 分钟人工足够；等真的忙不过来再自动化。

## 十三、决策记录

### 已定（2026-11-26）

| # | 决策 | 影响 |
|---|---|---|
| 1 | **公开站先做海外** | `boringtime.cn` + Cloudflare（单 Worker，同源）；不办 ICP；国内用户先用桌面端私人闭环 |
| 2 | **官方种子不标记、后台可查** | 前台不做区分标记（保住「海」的幻觉）；`gallery_bottles.seed=1` 后台可见；上限为真实内容 50% |
| 3 | **新闻线索由独立爬虫系统提供** | 本仓库只定义线索契约（第五节）；爬虫不进 monorepo；**没有任何自动发布路径** |

### 决策 2 的补充说明

不标记是有代价的：万一被用户发现「有些瓶子是官方写的」而没有标注，会被认为欺骗。
所以必须守住三条：

1. 种子**永不进入私池**——用户捡不到，不存在「我回了官方瓶子没人理」
2. 后台概览常驻显示种子占比，超过 30% 就红色告警（比 50% 红线更早）
3. **真实内容占比只增不减**：真实内容每增长，种子就按比例淘汰

### 决策 3 的补充说明

爬虫「先不用写」，但**契约先定**（见第五节）。这样爬虫系统可以在任何时间、由任何技术栈实现，
只要它认 `NewsLeadPush`。本仓库的实现顺序不受爬虫进度阻塞——
新闻编排界面可以先接收「手工录入的线索」（同一个接口的另一种调用方）。
